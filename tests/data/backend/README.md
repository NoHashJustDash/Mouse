# Native backend fixtures

Original deterministic synthetic networks, generated by
`python -I -m mouse_tools.make_backend_fixtures --output-dir tests/data/backend`.
These are test fixtures, not chess nets or reference neural outputs. Body format
123 explicitly denotes a synthetic body; the backend dispatches from tensor/head
contracts rather than assuming an architecture.

All ONNX files use opset17, float32 I/O and dynamic batch. For each independent row,
`s = sum(planes)` over the 112x8x8 input elements:

- `policy[j] = s * ((j % 17) - 8) / 16`, for j=0..1857.
- `wdl = softmax([s, 0, -s])` in W,D,L order.
- `mlh = max(s + 2, 0)`.

`valid.onnx` checks complete input-dependent output, dynamic rows, padding,
consecutive changed inputs, warm-up and concurrent callers. `nonfinite.onnx`
adds `1/(1-s)` to policy: zero-filled warm-up is finite, but s=1 produces Inf,
allowing a real inference result to test failure atomicity. Other heads remain
finite. `wrong-precision.onnx` has the valid graph but deliberately unsupported
precision metadata; consumer construction must reject it.

The generator and Python tests independently validate numerical formulas and
byte-for-byte regeneration of all tracked fixtures. Metadata source SHA is a
hash of the fixture provenance string, not a real weight file. All content is
Mouse-owned GPL-3.0-or-later; no upstream source/table/network is copied.

`failure-after-valid.bin` uses the MOUSEIN1 transport (two rows,112 planes,
2704 bytes). Only plane0 is populated: mask1/value2 in the first row and
mask1/value1 in the second. With `nonfinite.onnx --buckets1`, the first
evaluation succeeds and the second fails; the CLI must publish no partial binary output.

`oom.onnx` is an original allocation-stress graph, generated separately by
`python -I -m mouse_tools.make_oom_fixture --output tests/data/backend/oom.onnx`.
It declares the same named `batch` interface but is intended only for actual
batch1 with native CUDA, `--precision fp32 --buckets 1`. It reduces the input to
one scalar, expands it to `[1, 17179869184]`, applies `Sin`, then reduces and
normalizes by the element count. All three valid heads depend on that result;
the formulas above use `mean(sin(expanded_input_sum))` in place of `s`.

The default requests a **64GiB float32 intermediate** (68,719,476,736 bytes).
The ONNX file contains only small constants and shape metadata; generation does
not allocate this intermediate. **Never execute the default graph on CPU.**
CPU numerical tests explicitly generate the 16-element analogue, which computes
the same heads and preserves the stress chain through ORT optimization. The
large graph is inspected and regenerated without running it. `--elements` is
bounded to 1..2^34; the CLI reports both planned tensor bytes and actual file size.
A real CUDA OOM gate must observe the allocator failure, a nonzero engine exit
and zero stdout; graph dimensions alone are not evidence of an observed OOM.

Pinned CUDA operator registrations were checked in
[ORT 1.22.0 cuda_execution_provider.cc](https://github.com/microsoft/onnxruntime/blob/v1.22.0/onnxruntime/core/providers/cuda/cuda_execution_provider.cc)
and its reduction implementation. No upstream code is copied.

`search-nonfinite.onnx` is the search CLI failure fixture. Its policy offset is
the reciprocal of `float(sum(planes) == 0)`: zero-filled constructor warm-up
remains finite, while every nonzero row sum produces Inf. Positive classical
chess planes therefore exercise a real inference failure after construction.
The generator and CPU numerical regression validate both positive and negative
nonzero sums; existing fixtures remain byte-identical. It is never a chess net.

## Full-pool validation fixtures

`warmup-nonfinite.onnx` is an original dynamic three-head graph with the same
metadata and input-dependent heads as `valid.onnx`. Its policy offset is
`Reciprocal(scalar - scalar)`, so every finite input, including every all-zero
constructor warmup, produces nonfinite policy. WDL/MLH use the unchanged
base-fixture expressions and remain finite for the tested bounded inputs.
Construction must fail before returning a backend.

`padding-nonfinite.onnx` adds an original batch-coupled policy offset. It computes
`batch_nonzero = ReduceSum(Abs(scalar), axis=0) > 0` and
`invalid = batch_nonzero AND scalar == 0`; the offset is `1 / (1 - float(invalid))`.
All-zero warmup batches are finite. Nonzero logical rows are finite with offset1.
A zero row beside nonzero rows has infinite policy, so CUDA logical N=3 padded
to physical N=4 must reject the entire call even though all logical rows are valid.
CPU actual N=3 accepts those same inputs. The tracked GPU regression requires
real CUDA fp32 and explicit DLL directories; CPU execution is only its control.
Both fixtures are generated by `mouse_tools.make_backend_fixtures`; no upstream
graph or serialized protobuf bytes were copied or manually edited.
